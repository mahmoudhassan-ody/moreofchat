`base.py` — the port. Async, minimal:

```python
class LLMProvider(Protocol):
    name: str
    async def complete(self, *, model: str, messages: list[Message],
```

## Task 16b: The workers

Added on 2026-08-17, after Task 16. Not in the original plan and it should have been: Task 16's acceptance says "the full turn runs from a real WhatsApp message", and with nothing consuming the queue the message stopped there. The webhook enqueued into a Protocol with no implementation behind it.

**Files:**
- Create: `src/moc/workers/inbound.py`, `src/moc/workers/outbound.py`, `src/moc/workers/streams.py`
- Create: `src/moc/channels/valkey.py`, `src/moc/agent/conversations.py`
- Create: `config/workers/queues.yaml`
- Create: `migrations/versions/0005_conversation_thread_key.py`
- Create: `tests/workers/test_pipeline.py`

**Streams, not lists.** A consumer group gives at-least-once delivery with an explicit ack, so a worker that dies mid-turn leaves its entry pending for another worker to claim. `LPOP` loses the message the instant the process holding it stops, and the customer is left unanswered with nothing anywhere to show it arrived.

**Migration 0005 was not optional.** `conversations` held state and a tenant and nothing identifying *whose* thread it is, so the worker could create rows and never read one back. Every message would have started a fresh conversation, slots would never carry across turns, and edu-0004 would fail in a way that reads as a model problem rather than a schema one.

**Tests run against real Valkey**, on a separate database index. A fake queue re-proves the Protocol; the design depends on consumer groups, pending entries and acks, and only the real thing exercises those.

**Acceptance:** a signed webhook produces a sent reply end to end, with real streams and fakes only at the two provider edges. Met.

## Week 2 exit criteria

Rewritten on 2026-08-17, at the close of the week, to match the task list. The
original checklist carried two items — a full eval report and `eval-judge`
green in CI — that no task in this plan delivers: both need a **case runner**,
which appears in no task's file list. A checklist that cannot be satisfied by
completing every task in the plan it belongs to is not a checklist, it is a
second unwritten plan, and the honest fix is to move those items rather than to
mark them done. They are now listed under P1 with the reason.

Two items were added: the workers were built after Task 16 because without
them the webhook enqueued into nothing and the pipeline could not be exercised
end to end, which is what the first criterion has always asked for.

- [x] A scripted WhatsApp conversation completes end to end — signed webhook →
      Valkey stream → agent worker → orchestrator → outbound stream → adapter.
      Real streams; fakes only at the two provider edges. With retrieval still
      a seam the turn routes to the script's fallback, which is the correct
      turn for an un-ingested tenant and exercises every link in the chain.

      proven by sabotage
- [x] `pytest -m live` green with keys; full suite green without them
- [x] Prompt caching demonstrated: `cached_tokens > 0` on a repeated call
- [x] At-least-once delivery holds: a failed turn leaves its entry pending, a

## Deliberately not in week 2

- Retrieval ingestion, Qdrant sync, fusion (P1)
- **The eval case runner (P1).** Nothing drives the orchestrator over
  `evals/cases/*.yaml` and collects replies for the judge to grade, so the 22
  worked examples do not yet run through both stages and `eval-judge` stays
  gated. It waits on the retrieval decision rather than on effort: a case
  supplies `gold_chunks`, and whether the runner feeds those directly or runs
  real fusion over a fixture corpus determines what the numbers mean. Answering
  that twice is worse than answering it once, late. `eval-full` and
  `eval-judge` both fail loudly in CI naming this gap rather than greening on
  nothing.
- **The `channel_accounts` table.** A Protocol seam today. It is tenant-scoped
  and it is the one lookup RLS cannot scope, because it runs *before* a tenant
  context exists — its job is to establish which tenant a message belongs to.
  Needs a narrowly-privileged lookup role or a bootstrap policy, which is a
  security decision and not a side effect of a webhook task.
- Instagram, Messenger, Email (P2)
- Agent inbox (P1)
- The 230 real eval cases — Track A, human work, unblocked by none of this

## Note on measurement

Until the mined corpus lands, the judge grades 22 worked examples — enough to prove the machinery, not enough to trust a provider comparison. **Do not conclude anything about which provider is better on Egyptian Arabic from 22 cases**, and do not pin the answer-composition primary on that basis. That decision waits for the real suite.
